Report the validation pipeline status. Never rely on a session-start summary — read the files now.

## Steps

1. Find ideas: `ideas/*/state.json` in the current workspace. If `$ARGUMENTS` names a slug, report only that idea; otherwise report all (and if none exist, say so and point to `new-idea`). For each idea, also read the `cycles` index and every fragment `cycles/<id>/state.json` — report per cycle (a locked C1 plus an active C2 are two lines, not one).
2. **Pre-LOCK reconcile (v1.13.0, first mechanical step, before reading anything for the report below)**: for each cycle that has **not** reached LOCK (the mirror-image scope of the `reconcile` skill, which is post-LOCK only), run `node "${CLAUDE_SKILL_DIR}/../../scripts/reconcile-pre-lock.js" <idea-or-cycle-dir> --json`. Surface any deterministic divergences (each with a proposed patch) and non-deterministic open questions; apply a proposed patch only on the user's explicit confirmation, via `state-write.js` — never automatically. A cycle already past LOCK is skipped here (that is `reconcile`'s scope).
3. For each idea, read `state.json` and report, in the user's language:
   - **Post-launch validation** (`post_launch_validation`, only when the key is present — absent means V1 has never been deferred): report `status`, `reopen_on`, and (once set) `mvp_release_declared_at`. **When `status: "reactivated"`, flag it first and loudly** — before Position and everything else — real V1 evidence collection is now due (a controlled MVP release was declared against a deferred V1); point at `stage-2-validate` to run it for real. When `status` is `pending`/`active`, report it plainly alongside the gate summary (below); no urgency framing until it is `reactivated`.
   - **Position**: current stage and what the next concrete action is (name the exact task, e.g. "0.4 — score beachhead segments", not "continue stage 0").
   - **Gates — four separate metrics (v1.13.0), never conflated into one signal:**
     1. **Work completion %** — artifact status counts (draft/ready/locked) for the idea's active stage(s), computed deterministically by `node "${CLAUDE_SKILL_DIR}/../../scripts/status-metrics.js" <idea-or-cycle-dir> --json` (`work_completion`). A stage with zero artifacts written yet reports "no artifacts yet", never a fabricated 0%.
     2. **Formal gate compliance** — counts of `gates.*.status` against the closed enum (`passed`/`pass_with_deviation`/`failed`/`deferred`/`open`/`pending`/`in_progress`), also from `status-metrics.js` (`gate_compliance`), plus `state.blueprint.gate.status` (BP) reported separately since it lives outside the frozen per-cycle `gates` object. For failed gates: which gate the work returned to (method-rules §5). **V1 `deferred`** is reported distinctly from `open` (V1 has no accepted-open path) — name `deferred_reopen_on` and point at `post-launch-validation-register.md`; never describe it as "V1 passed" or "V1 open".
     3. **Evidence confidence** — the ledger's grade distribution via `node "${CLAUDE_SKILL_DIR}/../../scripts/validate-evidence-ledger.js" <idea-dir>/evidence-ledger.md --json --summary` (`grade_histogram`), read alongside `gates.V3.evidence_grade_observed` (the grade actually backing the money gate). This metric is deliberately NOT reduced to one number by this skill — a histogram plus V3's observed grade, reported together, is more honest than averaging them into something that looks precise and is not.
     4. **Build readiness** — LOCK / blueprint (BP) / cold-start status. This is the existing "Blueprint phase" reporting below, folded in here as its own named metric rather than duplicated: if LOCK has not passed, build readiness is "not yet" full stop; if LOCK passed and no `blueprint` block exists, readiness is "stage 6 not started"; otherwise report blueprint `status` and gate BP `status` (see the **Blueprint phase** bullet for the full detail this metric summarizes).

     Per-gate status is also reported with six explicit fields (v1.13.0) instead of the old ambiguous "accepted-open" line — computed from fields Patches 1–2 already added, no further schema change: **`analysis_complete`** (true once the gate has been formally attempted at least once, i.e. `status` is anything other than `pending`/`in_progress`) · **`gate_passed`** (`status === "passed"`, a clean pass with no carried caveats) · **`risk_accepted`** (`status === "pass_with_deviation"` — deviations knowingly carried forward per `gates.<g>.deviations[]`) · **`validation_deferred`** (`status === "deferred"`, legal only on V1 — never conflated with `risk_accepted` or with `open`, per the invariant that deferred is a structurally distinct third bucket) · **`revisit_phase`** (for `pass_with_deviation`: the union of `deviations[].revisit_phase`; for `deferred`: "post-launch, when V1 is re-run for real" per `post_launch_validation.reopen_on`; otherwise null) · **`blocks_current_phase`** (`status === "failed"` and this gate is a prerequisite, per `method-rules-gate-contracts`' `Requires` column, of a task in `state.active` — a failed gate blocks forward progress on whatever depends on it, per method-rules §5). An `open` gate sets none of `gate_passed`/`risk_accepted`/`validation_deferred` — it is its own fourth thing (an honestly recorded untested assumption), named as `open` and left there rather than folded into any of the six fields.
   - **Thresholds**: signed or not; if signed, date.
   - **Kill criteria**: each with days remaining; anything overdue gets flagged first and loudly. **Stale-triggered check (v1.13.0)**: run `node "${CLAUDE_SKILL_DIR}/../../scripts/detect-stale-criteria.js" <idea-dir> --json` — any criterion still `status: "triggered"` that a later `decision-log.md` row plainly resolves is surfaced with its proposed patch (`cleared`/`retired`); apply it only on the user's explicit confirmation, via `state-write.js`, never automatically (same posture as the pre-LOCK reconcile step above and this plugin's retention-duty disposal rule).
   - **Participant-data retention duties** (`privacy.retention_duties`, only when non-empty): report BEFORE ordinary next actions — anything past `delete_by` and not `disposed`/`extended` is named with its manifest ref and the note that disposal needs the founder's explicit approval over the exact files. Never delete anything here; `status` only reports.
   - **Waiting on**: handoff items pending with the user — report each as `what` · `resume_when` (the exact condition that would unblock it) · `owner` · `expires_or_recheck_at`, and flag any entry that is past its re-check date or has no `resume_when` at all (an entry with no resume condition is indistinguishable from an abandoned one — offer to define it or drop it). These are usually the critical path.
   - **Blueprint phase** (only when `state.blueprint` exists): cycle, status, gate BP status. If LOCK passed but no `blueprint` block exists, the next concrete action IS starting stage 6 — say so explicitly (build never starts straight from the pack). If `in_progress`, name the next unfinished row from `blueprint-overview.md`'s resume-ledger index rather than "continue stage 6". If locked with amendments: report the last BA id, and raise the **amendment-density signal** loudly — ≥3 amendments targeting one FS, or any amendment whose scope test came back YES, means the blueprint was under-specified there or scope is moving (method-rules §13 instinct: stop and look, don't keep patching); recommend reviewing that FS or running reconcile. When the blueprint is `locked`, say that build can start here: the session already carries the build contract, `/saas-idea-brainstorm:spec` resolves any id, and `spec-gap` routes a defect. Name `handoff-to-build` **only** if the code lives in a separate repository — and then mention it again after any amendment, since an amendment a build session in another repo cannot see has not landed.
   - **Post-LOCK maintenance** (only when a cycle is locked or `maintenance` is non-empty): last reconcile (id, date, intake authority) or "never reconciled"; current baseline head; **drift boundary status** — if any drift-inbox `drift_id` exceeds `last_reconcile.consumed_through` (the exact check; timestamps are only the hooks' approximation), flag loudly what is blocked (pack issuing/relabeling, validation runs, switch-mode) and recommend `reconcile`; unconsumed drift-inbox rows; armed `health_criteria` with days remaining (overdue = flag first, like kill criteria); signed validation runs whose confirmation window is open or expired unrun; `blocking_claims` (contradicted-retro) if any.
   - **Capabilities**: last audit date and rung implications ("scraping unavailable → V1 mining runs at baseline; run setup-audit after connecting to upgrade").
   - **Budget**: spent vs cap, if a cap is set.
4. End with a one-line recommendation of the single highest-leverage next action across all ideas.
5. If any `state.json` is unparsable, report it as damaged and offer to repair from the artifacts (artifacts are ground truth; state is an index).
