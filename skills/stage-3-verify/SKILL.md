Stage 3: verify. Starts as soon as the assumption map (0.5) shows a deadly feasibility assumption — do NOT wait for stage 2 to finish (if verify fails, all validation work on that direction is wasted). Two evidence types, never interchangeable: "the demo works" ≠ "people want it", and "people are in pain" ≠ "the AI is good enough". Load `method-rules`; read `state.json`. Templates: [templates.md](templates.md).

## Gate R1 — can we do it at the required quality (error-analysis-first)

For plain SaaS this gate is light. For AI-core products it is where most products silently die post-launch. The order is **error-analysis-first** — never write evals for imagined errors.

1. **Dirty spike** (`spike/`): core only — real input → processing → output. No UI, no auth. Real data sources by rung: public datasets in the domain (baseline); user-provided real files in `private/` (handoff — ask the interviewed/waitlist contacts, one more reason stages 2∥3 run together); a "value-for-data" exchange page (market-evidence). Maintain `spike/data-manifest.md`: for every real dataset/file used — source, owner, permission obtained (how), sensitivity, storage location (`private/` for anything personal). No real customer data enters the spike without a manifest row.
2. **Error analysis** (`error-analysis/` directory): run the spike over real data; read outputs and note errors (open coding). Reference discipline (Hamel/Shreya): review ~100 traces to start; cluster into a failure taxonomy (axial coding); **stop-rule**: ~20 consecutive traces with no new failure category = saturation. **Token discipline without write races**: each forked subagent processes one fixed batch (~10–20 traces) and writes its own immutable file `error-analysis/batch-NNN.md`; after ALL workers finish, the coordinator performs a deterministic merge into `error-analysis/summary.md` — workers never touch a shared file, and only category summaries enter the main context. Criteria drift is normal — revise while reading. **Judge evidence rules (gate-contracts)**: deterministic code-checked metrics on real data = grade C; **subjective quality judged by an LLM without human-labeled anchors = grade D, diagnostic only — it cannot satisfy the R1 PASS metric**. Invite the user to label a small anchor set (30 minutes on 20–50 outputs) — with ~75–90% judge–human agreement the judge's verdicts count as C; without anchors, subjective-quality R1 can only be OPEN. Separate **fix-now bugs** (just fix) from recurring failure modes (those get evals).
3. **Eval harness** (`eval/`): code checks for everything deterministic (schema, format, latency, forbidden content) FIRST; LLM-as-judge only for genuinely subjective criteria — **binary pass/fail, one evaluator per criterion**, judge prompt treated as production prompt. Alignment: if the user labels a held-out set, measure judge–human agreement (~75–90% required to trust the judge); autonomously, measure cross-model agreement and grade accordingly. Synthetic test data: generate along structured dimensions, never bare "give me test queries".
4. **Three shaping questions** (`promise-scope.md`): (a) quality vs the customer's acceptance threshold from V1/V2 evidence — set `thresholds.r1_eval_pass_pct` BEFORE the scored run (90% is fine for suggestions, nowhere near enough for consequential replace-a-human work); (b) failure style — visibly wrong vs plausibly wrong? plausibly-wrong forces human-in-the-loop in the design; (c) marginal cost per use vs the V3 price — AI unit economics can be negative by design; catch it here.
5. **Hard constraints**: data you can't get, latency, integration limits.
6. **Gate R1**: eval ≥ threshold on real data + marginal cost < price with livable margin + every known failure mode has a design answer. Fail → three exits, all product-direction changes: narrow the problem (nail 1 case, not average-10) / add human-in-the-loop (repositioning "autopilot" → "assistant") / return to 2.5 for a new direction. If **no representative real data is obtainable at all** (private workflow, no customers yet, nothing public): R1 may be accepted **OPEN** — and before the gate check you must **materialize the three OPEN deliverables** (templates in [templates.md](templates.md)): (a) feasibility-risk dossier = promise-scope's risks section, (b) `data-acquisition-plan.md` (how real data WILL be obtained, from whom, by when), (c) `eval/README.md` stating why no evaluation was possible. Per gate-contracts this downgrades the final pack to **Pre-feasibility Hypothesis Pack** — feasibility itself is an untested assumption and the pack says so on line 1. **Lock on pass: the promise scope — what the product promises and refuses to promise** (direct input to positioning).

## Gate R2 — does value actually reach the user

Feasibility ≠ delivered value. End-to-end check on real work.

1. Rungs: *handoff (original method)* — user runs concierge/Wizard-of-Oz for 3–5 committed customers (they don't need to know it's manual behind the scenes), reports back (grade A when commitments attach, B for measured outcomes); *autonomous (AI-core + willing contacts)* — **automated pilot: the wizard is the model itself** — deliver spike outputs on contacts' real work via email/web (grade B outcomes; **every delivery to a real contact is an outward action: per-send user approval, journaled**); *analysis mode floor* — value dry-run: run the spike end-to-end on realistic sample workloads, compare outputs against the promise (grade C, R2 recorded OPEN with `concierge-kit.md` ready).
2. **Measure outcomes, not sentiment** (`concierge-kit.md` log): real hours saved; is the output USED downstream (into their report, sent to their client) or received-and-shelved?
3. **Proto-retention**: does anyone come back a second time unprompted? Earliest measurable retention signal — and retention can't be bought back with marketing later.
4. **Manual-ops log**: every step performed by hand (or by you) during delivery. This log IS the true MVP spec — more accurate than any imagined spec.
5. **Gate R2**: measured outcomes match the problem-hypothesis promise + unprompted returns exist (or OPEN + kit). **Lock on pass: the real core loop + the observed aha moment** — from observation, never conjecture.
